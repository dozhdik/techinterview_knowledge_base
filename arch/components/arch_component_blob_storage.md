# Blob Storage

## Назначение
Blob Storage — это компонент для хранения больших бинарных объектов: изображений, видео, документов, архивов, резервных копий и других файлов. Он нужен, когда данные слишком велики или слишком плохо подходят для хранения в реляционной базе данных. В system design blob storage обычно выступает как дешёвое, масштабируемое и долговечное хранилище для неструктурированных данных. Шаблон карточки и обязательные секции здесь соответствуют структуре загруженного файла. :contentReference[oaicite:0]{index=0}

## Как работает
Blob storage хранит данные как отдельные объекты, у каждого из которых есть уникальный ключ, бинарное содержимое и набор метаданных. Приложение обычно не хранит сам файл в основной OLTP-базе, а сохраняет в базе только ссылку на объект, размер, MIME-тип, владельца и служебные атрибуты. При загрузке клиент отправляет файл либо через backend, либо напрямую в object storage по pre-signed URL. При чтении backend может вернуть ссылку на скачивание или проксировать объект сам, если нужна дополнительная авторизация или аудит. Для надёжности объекты реплицируются между несколькими узлами, а в managed-решениях часто и между зонами доступности. Для ускорения раздачи контента blob storage часто ставят за CDN, чтобы статику отдавать ближе к пользователю. Такие системы хорошо масштабируются горизонтально, но плохо подходят для сложных запросов, join-ов и частых мелких обновлений внутри объекта. На практике blob storage часто работает в паре с базой данных, очередями обработки файлов и сервисами генерации превью.

## Ключевые характеристики
- **Тип**: объектное хранилище
- **Масштабируемость**: горизонтальная
- **Консистентность**: чаще eventual, но зависит от реализации и операций чтения/записи

## Популярные реализации
- Amazon S3
- Google Cloud Storage
- Azure Blob Storage
- MinIO
- Ceph Object Storage

## Когда использовать
- хранение пользовательских изображений, видео, документов и вложений
- хранение статических файлов для web/mobile приложений
- резервные копии, архивы, логи, data lake
- хранение медиа для систем вроде chat, notification attachments, video platforms

## Когда НЕ использовать
- когда нужны сложные SQL-запросы по содержимому объекта
- когда данные маленькие, часто обновляются и требуют транзакционной логики
- когда нужен low-latency random read/write как у in-memory cache или block storage
- когда объект нужно постоянно модифицировать по частям, а не читать/писать целиком

## Trade-offs
| За | Против |
|----|--------|
| Хорошо подходит для больших файлов | Не подходит для сложных query-сценариев |
| Дешёвое масштабируемое хранение | Выше latency, чем у локального диска или cache |
| Высокая durability | Обычно требуется отдельная БД для метаданных |
| Удобно интегрируется с CDN | Возможны расходы на egress и операции |
| Подходит для user-generated content | Нет полноценной транзакционной модели как у OLTP БД |
