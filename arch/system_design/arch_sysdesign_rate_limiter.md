# Rate Limiter (Ограничитель запросов)

## Постановка задачи
Спроектируйте сервис для ограничения количества запросов от клиента за определённый промежуток времени. Система должна защищать API от злоупотреблений, обеспечивать fair usage и предотвращать DDoS-атаки.

## Шаг 1: Уточнение требований

### Функциональные требования
1. Ограничивать количество запросов от клиента (по IP, API key, user ID)
2. Возвращать ошибку 429 Too Many Requests при превышении лимита
3. Поддерживать разные лимиты для разных эндпоинтов/тарифов
4. Предоставлять заголовки о текущем использовании (X-RateLimit-*)

### Нефункциональные требования
1. Низкая задержка проверки (< 10ms)
2. Высокая доступность (> 99.99%)
3. Масштабируемость до миллионов RPS
4. Точность ограничения (минимальные ложные срабатывания)

### Уточняющие вопросы
1. Какой гранулярности лимиты? (глобальные, per-endpoint, per-user)
2. Какой временной интервал? (секунда, минута, час)
3. Нужна ли синхронизация между инстансами?
4. Какой уровень точности допустим?

### Допущения
- 10 000 запросов/сек на инстанс
- Лимит: 100 запросов/минуту на пользователя
- Хранение состояния 1 час
- 1 млн активных пользователей

## Шаг 2: Capacity Estimation

Запись: 10 000 записей/сек (обновление счётчиков)
Чтение: 10 000 проверок/сек
Хранилище: 1 млн пользователей × 1 час × 100 байт ≈ 360 ГБ/час (но с TTL очистка)
Память в Redis: ~10-20 ГБ для hot-данных

## Шаг 3: High-Level Design

Основные компоненты:
1. **API Gateway / LB**: принимает запросы, извлекает идентификатор клиента
2. **Rate Limiter Service**: проверяет лимиты, принимает решение
3. **Distributed Store (Redis)**: хранит счётчики с TTL
4. **Config Service**: управляет правилами лимитов

Поток данных:
- Request → Gateway → извлечь API key → Rate Limiter → проверить Redis → разрешить/отклонить → forward to backend

## Шаг 4: Deep Dive

### 4.1 Алгоритмы ограничения

| Алгоритм | Описание | Плюсы | Минусы |
|----------|----------|-------|--------|
| Fixed Window | Счётчик сбрасывается каждые N секунд | Простота, низкая память | Скачки на границах окон |
| Sliding Window Log | Хранит таймстемпы всех запросов | Точность | Высокая память |
| Sliding Window Counter | Комбинация двух окон | Баланс точности и памяти | Сложнее реализация |
| Token Bucket | Токены добавляются с фиксированной скоростью | Гибкость, burst-поддержка | Сложнее настройка |
| Leaky Bucket | Запросы обрабатываются с фиксированной скоростью | Сглаживание трафика | Не поддерживает burst |

**Выбор**: Sliding Window Counter для баланса точности и производительности.

### 4.2 Распределённая синхронизация

Проблема: несколько инстансов обновляют один счётчик

Решения:
- **Redis INCR**: атомарная операция, подходит для большинства случаев
- **Lua script**: атомарная проверка+инкремент
- **Rate limiter library**: Redisson, Guava RateLimiter с распределённым бэкендом


## Шаг 5: Trade-offs и альтернативы

| Решение | За | Против | Когда выбирать |
|---------|----|--------|---------------|
| Local in-memory cache | Очень быстро, нет сетевых вызовов | Нет синхронизации между инстансами | Один инстанс или допустимы неточности |
| Redis + INCR | Быстро, атомарно, распределённо | Сетевой вызов, зависит от Redis | Продакшн, несколько инстансов |
| Redis + Lua script | Атомарная проверка+инкремент | Сложнее отладка, блокировка ключа | Высокие требования к точности |
| Dedicated rate limiter service | Гибкость, централизованное управление | Доп. компонент, задержка | Крупные системы с разными правилами |

## Шаг 6: Bottlenecks и решения

1. **Redis как SPOF**: → Redis Cluster с репликацией и автоматическим failover
2. **Сетевая задержка**: → Локальный кеш с async sync, pipelining запросов
3. **Hot keys**: → Шардинг по user_id, использование hash tags в Redis
4. **Большое количество правил**: → Кэширование конфигурации в памяти, lazy load

## Критерии оценки интервьюером

| Уровень | Ожидания |
|---------|----------|
| Middle | Понимает алгоритмы, может реализовать Fixed/Sliding Window, знает про Redis |
| Senior | Сравнивает алгоритмы, обсуждает распределённые аспекты, предлагает fallback-стратегии |

## Типичные ошибки кандидатов

- Выбирают алгоритм без обоснования требований к точности
- Забывают про распределённую синхронизацию
- Не учитывают очистку старых данных (TTL)
- Не обсуждают мониторинг и алертинг при атаках
- Игнорируют graceful degradation при сбое rate limiter
