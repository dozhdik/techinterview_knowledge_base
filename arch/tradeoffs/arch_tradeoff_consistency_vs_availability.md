# Consistency vs Availability (CAP theorem)

## Суть компромисса
Теорема CAP утверждает: в распределённой системе при сетевом разделении (Partition tolerance — P) невозможно одновременно обеспечить сильную консистентность (Consistency — C) и полную доступность (Availability — A). При выборе архитектуры необходимо осознанно жертвовать одним из свойств в пользу другого, исходя из требований бизнеса.

## Вариант A: Strong Consistency (CP-системы)

### Преимущества
- **Линейная согласованность**: все узлы видят одни и те же данные в один момент времени
- **Предсказуемость**: чтение всегда возвращает последнюю записанную версию
- **Проще логика приложения**: не нужно обрабатывать устаревшие данные

### Недостатки
- **Сниженная доступность**: при потере связи с кворумом узлы блокируют запись/чтение
- **Более высокая задержка**: требуется синхронная репликация перед подтверждением
- **Масштабирование сложнее**: координация между узлами создаёт узкие места

### Когда выбирать
- Финансовые транзакции (баланс счёта, переводы)
- Системы бронирования (билеты, номера)
- Инвентаризация товаров с ограниченным запасом
- Любые сценарии, где неверные данные критичны

## Вариант B: High Availability (AP-системы)

### Преимущества
- **Высокая доступность**: система отвечает даже при потере части узлов
- **Низкая задержка**: запись подтверждается локально, репликация асинхронна
- **Лучшее масштабирование**: узлы работают автономно, меньше координации

### Недостатки
- **Eventual consistency**: разные клиенты могут видеть разные версии данных
- **Сложнее логика приложения**: нужно разрешать конфликты, обрабатывать устаревшие данные
- **Риск потери данных**: при сбоях до репликации возможны расхождения

### Когда выбирать
- Социальные сети (лайки, комментарии — допустима небольшая задержка синхронизации)
- Системы аналитики и метрик (агрегированные данные, не критична точность в реальном времени)
- Кеш-слои, сессии пользователей
- Глобальные системы с требованиями к низкой задержке

## Сравнительная таблица

| Критерий | Strong Consistency (CP) | High Availability (AP) |
|----------|-------------------------|------------------------|
| Доступность при разделении | Нет (блокировка) | Да (отвечает) |
| Актуальность данных | Всегда последняя версия | Возможно устаревшие данные |
| Запись | Синхронная репликация | Асинхронная репликация |
| Задержка | Выше | Ниже |
| Сложность для разработчика | Ниже | Выше (конфликты, версионирование) |
| Примеры | PostgreSQL (синхронная репликация), ZooKeeper, etcd | DynamoDB (default), Cassandra, Redis Cluster |

## Реальные примеры

- **ZooKeeper / etcd (CP)**: выбор в пользу консистентности для координации сервисов, где неверные данные приведут к рассинхронизации всей системы
- **DynamoDB (AP by default)**: выбор в пользу доступности для глобальных приложений, где пользователь предпочтёт увидеть чуть устаревшие данные, чем ошибку
- **Cassandra (настраиваемая)**: позволяет выбрать уровень консистентности на уровне запроса (ONE, QUORUM, ALL)

## Как обсуждать на собеседовании

1. **Начни с требований**: «Какая консистентность нужна для этого сценария? Допустимы ли устаревшие данные?»
2. **Покажи понимание CAP**: «При сетевом разделении мы не можем иметь и то, и другое — нужно выбрать приоритет»
3. **Предложи гибридный подход**: «Можно использовать CP для критичных данных + AP для некритичных»
4. **Упомяни PACELC**: «Помимо CAP, важно учитывать trade-off между latency и consistency даже без разделений»
