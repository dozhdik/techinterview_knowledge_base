# Monolith vs Microservices

## Суть компромисса
Выбор между монолитной и микросервисной архитектурой — фундаментальное решение на старте проекта. Монолит проще в разработке и деплое, но сложнее масштабируется. Микросервисы дают гибкость и независимое масштабирование, но требуют зрелости команды и инфраструктуры. Нельзя получить простоту монолита и масштабируемость микросервисов одновременно.

## Вариант A: Monolith (Монолит)

### Преимущества
- **Простота разработки**: один репозиторий, один деплой, единая кодовая база
- **Быстрый старт**: не нужно настраивать service discovery, API gateway, распределённый трейсинг
- **Проще тестирование**: end-to-end тесты запускаются локально без эмуляции сети
- **Транзакции**: ACID-транзакции в рамках одной БД, нет distributed transactions
- **Отладка**: стектрейс показывает весь путь выполнения, проще логирование

### Недостатки
- **Масштабирование**: масштабируется только вертикально или клонированием всего приложения
- **Технический долг**: со временем код становится связным, сложно вносить изменения
- **Деплой**: любое изменение требует деплоя всего приложения
- **Технологический стек**: сложно использовать разные языки/фреймворки для разных модулей
- **Отказоустойчивость**: баг в одном модуле может «уронить» всё приложение

### Когда выбирать
- Стартап на ранней стадии (команда < 10 человек, быстрый MVP)
- Внутренние инструменты с низкой нагрузкой
- Проекты с чёткими границами и стабильными требованиями
- Команда без опыта в распределённых системах

## Вариант B: Microservices (Микросервисы)

### Преимущества
- **Независимое масштабирование**: можно масштабировать только нагруженные сервисы
- **Гибкость технологий**: каждый сервис может использовать свой стек
- **Независимые деплои**: можно деплоить сервисы по отдельности без влияния на другие
- **Изоляция сбоев**: падение одного сервиса не обязательно ломает всю систему
- **Организационное соответствие**: команда владеет сервисом от кода до продакшена (Two Pizza Teams)

### Недостатки
- **Сложность инфраструктуры**: нужны service mesh, API gateway, distributed tracing, monitoring
- **Распределённые транзакции**: нужны Saga, eventual consistency, компенсационные транзакции
- **Сетевая задержка**: межсервисные вызовы медленнее ин-процесс вызовов
- **Сложность отладки**: нужно агрегировать логи из множества сервисов
- **Тестирование**: сложно запускать end-to-end тесты, нужны контракты и mocks

### Когда выбирать
- Крупная продуктовая компания с несколькими командами
- Высокая нагрузка с неравномерным распределением по функционалу
- Разные части системы имеют разные требования к доступности/консистентности
- Частые изменения в отдельных частях продукта

## Сравнительная таблица

| Критерий | Monolith | Microservices |
|----------|----------|---------------|
| Сложность разработки | Низкая | Высокая |
| Сложность деплоя | Низкая | Высокая |
| Масштабирование | Вертикальное / клонирование | Горизонтальное, гранулярное |
| Отказоустойчивость | Единая точка отказа | Изоляция сбоев |
| Транзакции | ACID, простые | Distributed, eventual consistency |
| Технологический стек | Единый | Разный на сервис |
| Команда | Одна команда на проект | Несколько команд, по сервису |
| Время выхода на рынок | Быстро | Медленнее (инфраструктура) |

## Реальные примеры

- **Monolith → Microservices**: Netflix, Amazon, Uber начинали с монолита, перешли на микросервисы при росте нагрузки и команд
- **Microservices → Modular Monolith**: некоторые компании возвращаются к модульному монолиту, если микросервисы оказались over-engineering
- **Hybrid**: ядро системы — монолит, высоконагруженные части вынесены в отдельные сервисы

## Стратегия миграции (если нужно)

1. **Start with monolith**: начать с модульного монолита с чёткими границами
2. **Extract when pain appears**: выносить сервисы только когда монолит начинает мешать
3. **Strangler Fig pattern**: постепенно заменять части монолита новыми сервисами
4. **Invest in infrastructure first**: настроить CI/CD, monitoring, logging до миграции

## Как обсуждать на собеседовании

1. **Начни с контекста**: «Зависит от размера команды, нагрузки, стадии продукта»
2. **Покажи понимание компромиссов**: «Монолит проще, но микросервисы масштабируются»
3. **Предложи эволюционный подход**: «Начать с модульного монолита, выносить по мере роста»
4. **Упомяни организационный аспект**: «Микросервисы требуют зрелости команды и процессов»

## Типичные ошибки при выборе

- Выбирать микросервисы «потому что модно», без реальных причин
- Дробить сервисы слишком мелко (наносервисы)
- Игнорировать стоимость инфраструктуры и операционных затрат
- Не учитывать зрелость команды и процессов
- Начинать с микросервисов на раннем стартапе
