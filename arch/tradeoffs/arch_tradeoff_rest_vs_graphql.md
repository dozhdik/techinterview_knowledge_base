# REST vs GraphQL

## Суть компромисса
Компромисс между REST и GraphQL — это выбор между простотой, предсказуемостью и зрелой HTTP-моделью с одной стороны и гибкостью выборки данных с другой. REST обычно проще в проектировании, дебаге, кешировании и эксплуатации. GraphQL позволяет клиенту забирать ровно те поля, которые ему нужны, и агрегировать данные из нескольких источников через одну схему. Но за эту гибкость платят усложнением серверной логики, защитой от тяжёлых запросов, более сложным caching и более дорогой observability. Правильный ответ на собеседовании не в том, чтобы объявить один подход “лучше”, а в том, чтобы показать, какой набор проблем решает каждый.

## Вариант A
### Преимущества
- Простая ресурсная модель и понятные endpoint-ы
- Хорошо сочетается с HTTP semantics: методы, статусы, caching
- Легче мониторить, rate limit-ить и дебажить
- Подходит для публичных API и простых CRUD-сценариев
- Отлично работает с CDN и стандартным кешированием

### Недостатки
- Возможны overfetching и underfetching
- Иногда клиенту нужно делать несколько запросов за связанными данными
- При росте продукта API может обрастать большим числом endpoint-ов
- Менее удобно для сложных frontend-экранов с сильно меняющимися требованиями к данным

### Когда выбирать
- публичные и partner API
- простые и средние CRUD-сервисы
- системы, где важны caching, predictability и низкая операционная сложность
- случаи, когда команда не хочет тащить дополнительную сложность схемы и resolver-ов

## Вариант B
### Преимущества
- Клиент запрашивает только нужные поля
- Удобно агрегировать данные из нескольких backend-источников
- Хорошо подходит для сложных frontend-приложений и BFF-layer
- Typed schema улучшает контракт между клиентом и сервером
- Упрощает эволюцию API без явного versioning на уровне endpoint-ов

### Недостатки
- Сложнее caching, особенно на edge и CDN
- Нужна защита от тяжёлых или слишком глубоких запросов
- Часто возникает проблема N+1 в resolver-ах
- Сложнее анализировать производительность одного “запроса”, чем в REST
- Повышается сложность авторизации, observability и cost control

### Когда выбирать
- сложные frontend-приложения с разными экранами и меняющимися data needs
- BFF / gateway слой над несколькими сервисами
- случаи, где дорого делать много round-trip к backend
- продукты, где нужна гибкая агрегация данных для разных клиентов

## Сравнительная таблица
| Критерий | Вариант A | Вариант B |
|----------|-----------|-----------|
| Простота эксплуатации | Выше | Ниже |
| Гибкость выборки | Ниже | Выше |
| HTTP caching | Отлично | Ограниченно |
| Edge/CDN fit | Хороший | Слабее |
| Защита от тяжёлых запросов | Проще | Сложнее |
| Скорость старта | Выше | Ниже |
| Typed schema | Обычно слабее | Сильнее |
| Агрегация разных источников | Менее удобна | Более удобна |

## Реальные примеры
- **Публичный API платформы**: часто выбирают REST, потому что он понятнее внешним интеграторам, проще документируется и лучше кешируется.
- **Frontend gateway для мобильного приложения**: часто выбирают GraphQL, потому что разные экраны хотят разный набор полей и не хочется плодить десятки специализированных endpoint-ов.
- **B2B интеграции**: чаще REST, потому что для внешних партнёров важнее стабильность, predictability и простота поддержки, чем гибкость query language.

## Как обсуждать на собеседовании
Не нужно продавать GraphQL как “современную замену REST” — это инфантильный ответ. Сильный ответ звучит так: REST выигрывает там, где важны простота, HTTP caching, predictability и низкая операционная сложность. GraphQL выигрывает там, где клиентам нужна гибкая выборка и агрегация данных через одну схему. Хороший кандидат также проговаривает риски GraphQL: N+1, сложный caching, query cost analysis, depth limiting и observability. Ещё лучше — сказать, что в реальной системе часто используют гибрид: REST для публичных и простых API, GraphQL для BFF или complex client data aggregation.
