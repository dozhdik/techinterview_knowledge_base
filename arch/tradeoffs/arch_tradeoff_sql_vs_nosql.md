# SQL vs NoSQL

## Суть компромисса
Выбор между реляционными (SQL) и нереляционными (NoSQL) базами данных — фундаментальное архитектурное решение. Нельзя одновременно получить строгую схему и гибкость, идеальную консистентность и горизонтальную масштабируемость. Выбор зависит от структуры данных, требований к консистентности и паттернов доступа.

## Вариант A: SQL (PostgreSQL, MySQL, Oracle)

### Преимущества
- **ACID-транзакции**: гарантия атомарности, консистентности, изоляции, долговечности
- **Строгая схема**: валидация данных на уровне БД, меньше ошибок в приложении
- **Сложные запросы**: JOIN, подзапросы, оконные функции, агрегации
- **Зрелость**: отлаженные инструменты, богатая экосистема, предсказуемость

### Недостатки
- **Вертикальное масштабирование**: сложнее шардить, чем в NoSQL
- **Жёсткая схема**: миграции при изменении структуры, медленнее итерации
- **Производительность на больших объёмах**: требует тщательной оптимизации индексов

### Когда выбирать
- Финансовые системы, где важна консистентность
- Сложные отношения между сущностями (много JOIN)
- Требования к отчётности и аналитике
- Небольшие/средние объёмы данных (< 1 TB)

## Вариант B: NoSQL (MongoDB, DynamoDB, Cassandra, Redis)

### Преимущества
- **Горизонтальное масштабирование**: шардинг «из коробки», линейный рост
- **Гибкая схема**: быстрая итерация, хранение разнородных документов
- **Высокая производительность**: оптимизация под конкретные паттерны доступа
- **Специализация**: key-value для кеша, document для контента, graph для связей

### Недостатки
- **Eventual consistency**: не все системы гарантируют strong consistency
- **Ограниченные запросы**: нет JOIN, сложнее выполнять аналитику
- **Дублирование данных**: денормализация требует дополнительной логики синхронизации

### Когда выбирать
- Высокая нагрузка на запись/чтение (миллионы RPS)
- Глобальное распределение (multi-region)
- Гибкая/меняющаяся структура данных
- Специфичные паттерны: кеш, сессии, события, графы

## Сравнительная таблица

| Критерий | SQL | NoSQL |
|----------|-----|-------|
| Модель данных | Таблицы, строки, связи | Документы, key-value, графы, колонки |
| Схема | Строгая, фиксированная | Гибкая, динамическая |
| Масштабирование | Вертикальное + сложное горизонтальное | Горизонтальное «из коробки» |
| Транзакции | ACID (полные) | BASE / ограниченные / eventual |
| Запросы | SQL, JOIN, агрегации | Специфичный API, ограниченные запросы |
| Индексы | B-tree, hash, composite | Зависит от реализации |
| Use case | Финансы, ERP, CRM | Соцсети, IoT, кеш, аналитика |

## Реальные примеры

- **PostgreSQL в Stripe**: выбор в пользу сильной консистентности для финансовых транзакций
- **DynamoDB в Netflix**: горизонтальное масштабирование для глобального стриминга с высокой доступностью
- **MongoDB в Adobe Experience Cloud**: гибкая схема для хранения разнородных пользовательских данных

## Как обсуждать на собеседовании

1. **Начни с требований**: «Сначала уточним: какая нужна консистентность? Какой паттерн доступа?»
2. **Покажи понимание trade-off**: «SQL даст нам ACID, но сложнее масштабировать; NoSQL масштабируется, но нужно продумать eventual consistency»
3. **Предложи гибридный подход**: «Можно использовать PostgreSQL для транзакций + Redis для кеша + DynamoDB для событий»
4. **Обоснуй выбор**: «Выбираю SQL, потому что... / Выбираю NoSQL, потому что...»
