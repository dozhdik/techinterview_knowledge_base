# Идемпотентность HTTP-методов и повтор запросов

## Определение

HTTP-метод идемпотентен, если предполагаемый эффект нескольких одинаковых запросов на состояние сервера совпадает с эффектом одного такого запроса. Это свойство описывает намерение операции, а не обязательное совпадение ответов или отсутствие журналирования каждого вызова.

## Какие методы идемпотентны

По HTTP-семантике безопасные методы, а также `PUT` и `DELETE` идемпотентны. `POST` и `PATCH` не имеют такой гарантии по определению метода. Реальная реализация сервера должна соблюдать заявленную семантику: выбор метода сам по себе не исправит обработчик, который создаёт повторные побочные эффекты.

## Пример повтора

Клиент отправил запрос на удаление ресурса, но соединение оборвалось до получения ответа. Повторный `DELETE` может вернуть другой код ответа, например если ресурс уже отсутствует, но предполагаемый эффект — отсутствие ресурса — остаётся тем же. Это не означает, что запрос не попадёт в журнал дважды.

При создании платежа через `POST` повтор без дополнительной защиты может создать дубликат. API может реализовать ключ идемпотентности: сервер связывает ключ и параметры операции с её результатом и распознаёт повтор. Правила хранения, срока действия ключа и обработки конфликтующих параметров определяет конкретный API.

## Границы и ошибки

- Идемпотентность не означает безопасный метод: `DELETE` изменяет состояние, хотя его предполагаемый эффект идемпотентен.
- Повторы должны учитывать таймауты, ограничение числа попыток и backoff; идемпотентность не гарантирует доступность сервиса.
- Результат повторного запроса и его статус могут отличаться; проверяйте контракт конкретного API.
