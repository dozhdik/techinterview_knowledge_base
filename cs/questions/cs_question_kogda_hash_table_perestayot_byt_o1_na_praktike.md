# Когда hash table перестаёт быть O(1) на практике

## Определение

Hash table обычно даёт `O(1)` в среднем для вставки, поиска и удаления, но эта оценка держится только при хорошей хеш-функции, контролируемом load factor и корректной реализации разрешения коллизий. На практике hash table перестаёт вести себя как `O(1)`, когда число коллизий растёт, rehash происходит слишком часто или операции начинают упираться в реальные свойства памяти и данных.

## Суть концепции

На собеседовании многие кандидаты повторяют мантру: “hash table — это `O(1)`”. Это упрощение годится только как стартовая фраза. Правильный ответ должен звучать жёстче: **в среднем `O(1)`, в худшем случае `O(n)`**.

Почему так? Потому что hash table зависит от распределения ключей по бакетам. Если хеш-функция распределяет ключи равномерно, а таблица не перегружена, доступ действительно близок к константному. Но если многие ключи попадают в одни и те же бакеты, операции начинают деградировать: приходится проходить цепочку элементов, пробовать несколько ячеек подряд или вызывать rehash.

Есть несколько основных причин деградации:

1. **Плохая хеш-функция**  
   Если она даёт много коллизий, таблица перестаёт быть почти-константной.

2. **Высокий load factor**  
   Когда таблица слишком заполнена, растёт число коллизий и ухудшается поведение поиска/вставки.

3. **Неблагоприятные данные**  
   Даже нормальная реализация может работать хуже, если вход специально подобран или структура ключей плохо сочетается с хешированием.

4. **Rehash / resize**  
   Отдельная операция вставки может внезапно стать дорогой, потому что таблица расширяется и все элементы перераспределяются заново.

5. **Практические эффекты железа**  
   Теоретически средняя сложность может оставаться `O(1)`, но cache misses, pointer chasing и плохая locality заметно ухудшают производительность на практике.

Нужно различать три уровня ответа:

- **Учебный**: hash table обычно `O(1)`.
- **Корректный**: average case `O(1)`, worst case `O(n)`.
- **Сильный практический**: даже без формального worst-case поведение может заметно деградировать из-за коллизий, load factor, rehash и свойств памяти.

Именно этот третий уровень обычно отличает кандидата, который реально понимает структуру, от того, кто просто выучил таблицу сложностей.

## Ключевые характеристики

- **Средняя сложность поиска / вставки / удаления**: `O(1)`
- **Worst case**: `O(n)`
- **Что влияет на производительность**:
    - качество хеш-функции
    - load factor
    - стратегия collision resolution
    - resize / rehash
    - распределение ключей
    - cache locality
- **Типовые стратегии разрешения коллизий**:
    - chaining
    - open addressing
- **Амортизированное поведение вставки**: обычно близко к `O(1)`, но отдельный rehash может стоить `O(n)`
- **Пространственная сложность**: `O(n)`
