# Экстрактивный поиск без LLM

При наличии локально сохранённых MiniLM и рабочего структурного индекса выполните следующую команду.

```bash
./scripts/run_rag.sh
```

Чат откроется по адресу `http://127.0.0.1:8000`. `POST /api/ask` сохраняет прежние поля ответа. `sources` содержит карточки, использованные при составлении ответа. `search_state` показывает итог отбора, а `related_materials` содержит отдельные рекомендации с ID, названием, областью, ссылкой и кратким исходным описанием при его наличии. `search_notice` появляется при переходе на текстовый поиск. Запрос по точному ID открывает полную карточку.

Во время запуска `GET /api/health` отвечает HTTP 503 со статусом `warming_up`. После однократной подготовки модели и индекса он возвращает HTTP 200 и `ready`. При отсутствии индекса, несовпадении с корпусом или ошибке загрузки API показывает `degraded` и поясняет причину. Текстовый поиск в этом состоянии доступен. Если структурный индекс отсутствует или устарел, выполните `.venv-rag/bin/python main.py passage-build` и перезапустите сервер. Подробные инструкции первоначальной установки приведены в [README](../README.md#установка).

Структурный индекс `_data/passage_index.sqlite3` содержит оригинальные блоки Markdown, пути заголовков, позиции, метаданные карточек и векторы. Абзацы, таблицы и ограждённый код сохраняются целиком. Длинный блок получает несколько окон эмбеддингов, исходный текст сохраняется. После изменения корпуса команда `passage-build` использует векторы неизменившихся записей. Команды `vector-*` продолжают работать со старым индексом. После изменения исходных карточек требуется обновить структурный индекс.

Поиск формирует независимые списки BM25 и семантических кандидатов по всему индексу, объединяет позиции через RRF и учитывает покрытие терминов вопроса. Точный нормализованный заголовок получает предпочтение для определения. Для запросов с самостоятельными частями поиск проходит по каждой части. Сервер проверяет свидетельства в разделах первых пяти карточек. Бюджет одной части зависит от её назначения. Для короткого определения или количественного запроса он составляет до двух блоков и 2 200 символов, для процедуры или проектирования — до пяти блоков и 6 100 символов. Сравнение, асимптотика и обычное объяснение получают промежуточный бюджет. Дополнительный блок должен добавить информацию и пройти проверку на повторы. Для карточек из другой области дополнительно нужна явная связь. Оригинальные блоки объединяются по заголовкам. Разные фрагменты длинного раздела сохраняются, а покрытие проверяется после окончательной сборки. Первый запрос обрабатывает до восьми частей. Остальные явно перечисляются для следующего сообщения. Явные зависимые части получают контекст предыдущего вопроса. При неясной отсылке к этапу или шагу чат просит уточнить вопрос.

```bash
.venv-rag/bin/python main.py search-diagnose "Как выбрать порядок столбцов составного индекса?" --domain cs
.venv-rag/bin/python main.py search-benchmark --split test --method hybrid --output /tmp/tech-benchmark.json
```

Диагностика показывает нормализованный вопрос, намерения, кандидатов каждого канала, объединённую выдачу, результаты повторной оценки, выбранные исходные блоки, причины допуска или отказа по кандидатам и оставшиеся части вопроса. Параметр `--depth 3|5|10` задаёт глубину проверки. Флаг `--links` включает экспериментальную проверку связей в пределах одного перехода. Для эксперимента с локальным Cross-Encoder задайте `KB_RERANKER_PATH` при запуске или `--method cross_encoder --reranker /путь/к/каталогу` в benchmark. Снятие переменной возвращает обычное ранжирование.

Для сравнения с исходным алгоритмом используйте `--method legacy` с прежним индексом. Для остальных методов достаточно структурного индекса.

Метрики, условия эксперимента и ошибки приведены в [отчёте benchmark](retrieval_benchmark.md).

## Индекс для эксперимента с E5

Команды используют локальный каталог с весами и отдельный SQLite-файл. Для штатного чата по-прежнему используется индекс MiniLM.

```bash
.venv-rag/bin/python main.py passage-build --e5 --model /path/to/e5 --index /tmp/e5-passages.sqlite3
.venv-rag/bin/python main.py search-diagnose 'Как работает Ingress-контроллер?' --index /tmp/e5-passages.sqlite3
.venv-rag/bin/python main.py search-benchmark --split development --method hybrid \
  --index /tmp/e5-passages.sqlite3 --depth 5 --output /tmp/e5-development.json
```

Критерии достаточности учитывают уровень косинусных оценок E5 отдельно. Экспериментальные модели и индексы хранятся локально. Итоги сравнения и ограничения описаны в [RAG_TEST.md](../RAG_TEST.md).

## Экспериментальный Extractive QA

QA работает через локальную модель с весами `model.safetensors`. Штатный веб-чат использует структурный отбор без QA. В режиме `all` модель проверяет ограниченный список блоков для каждой части, в `selective` она запускается при слабом результате или близких оценках кандидатов. Режим `off` отключает компонент.

```bash
.venv-rag/bin/python main.py search-diagnose \
  'Как развернуть односвязный список, не потеряв остаток?' \
  --qa-mode selective --qa-path /path/to/qa
.venv-rag/bin/python main.py search-benchmark \
  --cases evaluation/search_holdout_iteration3.json --split all --method hybrid \
  --qa-mode all --qa-path /path/to/qa --output /tmp/qa-results.json
```

Диагностика включает состояние `complete`, `partial`, `related_only`, `absent` или `clarification`. Границы указаны в исходном блоке. Разность логитов между найденным интервалом и вариантом без ответа используется как дополнительный сигнал. Чат и CLI выводят исходные блоки с контекстом. Экспериментальные результаты приведены в [RAG_TEST.md](../RAG_TEST.md).

## Поисковое представление карточек

Для сравнения доступны два дополнительных канала. Режим `metadata` ищет по полям карточки и кратким извлечениям из её разделов с помощью BM25F. Режим `questions` ищет по потенциальным вопросам с помощью той же MiniLM, что и исходный семантический поиск. Режим `combined` объединяет оба списка с BM25F и семантическим поиском по исходным блокам через RRF. Режим `off` используется по умолчанию, в том числе в веб-чате.

```bash
export HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1
.venv-rag/bin/python main.py representation-build --index /tmp/tech-representations.sqlite3
.venv-rag/bin/python main.py search-diagnose 'Как обработать события с резкими пиками нагрузки?' \
  --representation-mode combined --representation-index /tmp/tech-representations.sqlite3
.venv-rag/bin/python main.py search-benchmark \
  --cases evaluation/search_holdout_iteration4.json --split all --method hybrid \
  --representation-mode metadata --representation-index /tmp/tech-representations.sqlite3 \
  --output /tmp/tech-metadata.json
```

Команда построения читает Markdown и YAML и записывает отдельный SQLite-файл. При отсутствии `--index` файл создаётся в `_data/representation_index.sqlite3`. После обновления карточек экспериментальный файл нужно построить заново. В индексе сохраняются ID карточки, поле YAML либо раздел и позиция в Markdown, шаблон и текст потенциального вопроса. Для семантического канала диагностика показывает происхождение наиболее близкого вопроса. Дополнительные каналы меняют список кандидатов. Достаточность материала и текст ответа проверяются по исходным блокам.

`complete` означает, что при отборе нашлись свидетельства для всех распознанных частей вопроса. `partial` сопровождается списком частей без материала. Для `related_only` найдена тематическая близость либо постановка задачи без требуемого решения. `absent` означает, что достаточный или уверенно связанный материал не определён. При `clarification` требуется уточнить отсылку либо продолжить запрос отдельным сообщением. Эти диагностические состояния характеризуют результат отбора. Содержательная полнота проверяется по смысловой разметке в [RAG_TEST.md](../RAG_TEST.md).

Материалы по теме выбираются только для частей вопроса без достаточного ответа. Для карточки нужны совпадение по исходным материалам и семантическое сходство. Дополнительным свидетельством служит редкий термин в названии или тегах, сильное покрытие текста либо исходная постановка задачи. Система показывает до трёх материалов, исключая карточки из `sources`. При запросе без понятной отсылки чат просит уточнение.

## Прямой запрос карточки

Запрос, состоящий из полного названия, открывает исходную карточку так же, как запрос по ID. Поиск учитывает регистр, Unicode, лишние пробелы, кавычки и типографские разделители. Технические знаки в `C++`, `C#` и `.NET` сохраняются. Альтернативные имена и сокращения берутся из заголовков, явно сформулированных определений и необязательных YAML-полей `aliases` и `abbreviations`. При совпадении нескольких доступных карточек чат предлагает выбрать ID. В CLI можно сузить поиск флагом `--domain`.

Признак прямого запроса проверяется по всей строке. «Какая сложность BFS?» и «Чем BFS отличается от DFS?» проходят через отбор исходных фрагментов. Диагностика прямого запроса показывает поле `lookup`, ID и возвращённый материал. Прямой поиск использует текущие карточки и доступен без SQLite-индекса и эмбеддингов.

```bash
.venv-rag/bin/python main.py search --text 'Поиск в ширину BFS' --domain cs
.venv-rag/bin/python main.py search-diagnose '«Поиск в ширину BFS»!'
.venv-rag/bin/python main.py search-diagnose 'Какая сложность BFS?'
```

## Распознавание сущностей в содержательных вопросах

`search-diagnose` по умолчанию показывает распознанные сущности, позиции в запросе, возможные ID, роль и запрошенные свойства. В `retrieve` добавляется отдельный список карточек, которые проверяются даже за пределами обычной пятёрки. Режим `evidence` также показывает, какие выбранные фрагменты подтверждают временную и пространственную сложность и какая часть сравнения осталась непокрытой.

```bash
.venv-rag/bin/python main.py search-diagnose 'Какая сложность алгоритма CS-CONCEPT-016?'
.venv-rag/bin/python main.py search-diagnose 'Чем BFS отличается от DFS?' --entity-mode evidence
.venv-rag/bin/python main.py search-benchmark --cases evaluation/entity_holdout.json \
  --split all --method hybrid --entity-mode retrieve --output /tmp/tech-entities.json
```

В штатном веб-чате остаётся обычный гибрид. `KB_ENTITY_MODE=retrieve` или `KB_ENTITY_MODE=evidence` позволяет отдельно запустить эксперимент на текущем индексе. Режим `link` собирает диагностику без изменения отбора. Содержательные вопросы с ID используют указанные карточки и соответствующие разделы в любом режиме. Отдельная команда открытия сохраняется. При запросе более трёх карточек ответ перечисляет отложенные ID.

Индекс упоминаний использует записи прямого поиска и ограниченные варианты из определений и технических синонимов. Склонения проверяются по уменьшенному набору русских окончаний. При неоднозначном сокращении диагностируется набор вариантов. Без ясной привязки работает обычное глобальное ранжирование. Вопросы по примеру реализации, ограничениям и областям применения используют эвристические признаки текста и заголовков. Покрытие численных свойств оценивается по контексту численной оценки в исходном фрагменте.

## Контекст диалога

Чат передаёт до шести предыдущих пар «вопрос — завершённый ответ» в порядке от старой к новой. Из каждой пары в запрос входят исходный вопрос (до 1000 символов), до восьми ID источников (по 1–48 символов) и состояние поиска (`complete`, `partial`, `related_only`, `absent`, `clarification` или `null`). Пример тела для `POST /api/ask` и `POST /api/ask/stream`:

```json
{
  "question": "Сколько памяти он занимает?",
  "context": [
    {"question": "Что такое BFS?", "source_ids": ["CS-CONCEPT-016"], "state": "complete"}
  ]
}
```

Поле `context` необязательно и может быть пустым массивом. Оба маршрута сохраняют существующие поля ответа. Итоговое событие потока содержит тот же результат в поле события `type: final`. При неоднозначной ссылке чат показывает ответ с `search_state: "clarification"`, предлагает уточнить тему и возвращает пустой список `sources`.

Сервер восстанавливает тему по вопросам и проверяет ID по доступным карточкам текущего корпуса. Списки прошлых источников и состояния нужны для диагностики. Тема следует из явно названных технологий и разрешённых продолжений. Для продолжения гибридный поиск по всему корпусу проверяет также карточки унаследованных сущностей. Ответ состоит из исходных фрагментов. При отсутствии свидетельств сервер возвращает частичный ответ, связанные материалы или отказ. Контекстные запросы выполняются экстрактивно при любом значении `RAG_ENABLED`. Прямое открытие по точному ID или названию имеет приоритет.

История восстанавливается из `localStorage` браузера. Кнопка очистки удаляет её и отменяет текущий поиск. Оборванные запросы и ошибки API исключаются из отправляемой истории. Самостоятельный запрос может начать новую тему. Для возврата к давно обсуждавшейся теме укажите её название или ID, если она вышла за пределы окна из шести реплик.

```bash
.venv-rag/bin/python main.py conversation-diagnose \
  'Что такое BFS?' 'Сколько памяти он занимает?' \
  'А чем он отличается от DFS?' 'Какова сложность обоих?'

for strategy in baseline naive structured; do
  .venv-rag/bin/python scripts/check_conversation.py \
    --strategy "$strategy" --split holdout --diagnose --output "/tmp/dialogues-$strategy.json"
done
```

Запускайте контрольные запросы после состояния `ready` у `/api/health`. Первый вариант передаёт один вопрос, второй склеивает его с одним предыдущим вопросом, третий использует поле `context`. Отложенная выборка, ручная оценка фактов и ограничения описаны в [RAG_TEST.md](../RAG_TEST.md#conversational-retrieval-и-разрешение-контекста-диалога).

## Названия технологий и псевдонимы

Для дополнительных названий карточки используется YAML. В `aliases` записываются общеупотребительные эквиваленты или устойчивые варианты написания. `abbreviations` содержит принятые сокращения. Полное исходное название сохраняется. Варианты языка допустимы, если обозначают тот же предмет. Связанные технологии, частные реализации и целые вопросы описываются в карточках и связях между ними.

```yaml
aliases:
  - Быстрая сортировка
  - Quicksort
```

Точное название проверяется первым. Для короткой тематической фразы поиск пробует убрать одно начальное родовое слово, например «алгоритм» или «структура данных», и сверить оставшийся термин с названиями. Ограниченная нормализация склонений применяется к полному термину. Смысловые слова и уточнения сохраняются в содержательных вопросах. Совпадение по YAML или названию передаёт найденную карточку на проверку вместе с другими результатами гибридного поиска. Из другой карточки используется фрагмент, который относится к названной сущности. Для сравнений и количественных ответов проверяются обе стороны и требуемые свойства. Коллизии альтернативных названий и сокращений могут вернуть просьбу уточнить карточку.

Редакторская проверка и обновление индекса после изменения YAML выполняются из корня проекта.

```bash
.venv-rag/bin/python main.py validate
.venv-rag/bin/python scripts/audit_terminology.py --output /tmp/terminology-audit.json
HF_HUB_OFFLINE=1 TRANSFORMERS_OFFLINE=1 .venv-rag/bin/python main.py passage-build
.venv-rag/bin/python main.py vector-status
```

Структурный SQLite сверяет хеш исходных файлов. После изменения только этих полей `passage-build` регистрирует новый хеш и повторно использует векторы прежних фрагментов. Терминология применяется к запросу и лексическому ранжированию. Эмбеддинги исходных блоков строятся из заголовка и текста карточки. После обновления запустите сервер и проверьте состояние `ready` на `/api/health`. Итоги аудита и методика сравнения приведены в [RAG_TEST.md](../RAG_TEST.md#терминологическое-покрытие-и-предотвращение-подмены-сущностей).
