# RAG в веб-чате TechInterview

RAG-путь для обычных вопросов реализован в `kb/rag.py` и `web/server.py`: поиск фрагментов в локальном векторном индексе, передача ограниченного контекста генератору и ответ со ссылками на использованные карточки. Для вопросов с явным ID сохраняется прямой показ карточки и сообщения о неизвестных или незаполненных ID.

## Включение

Нужен запущенный сервис с API, совместимым с `POST /v1/chat/completions`. Адрес и имя модели задаются через переменные окружения перед запуском веб-сервера:

```bash
export RAG_BASE_URL="http://localhost:11434/v1"
export RAG_MODEL="имя-установленной-модели"
venv/bin/python main.py vector-build
venv/bin/python -m uvicorn web.server:app --reload --port 8000
```

Для сервиса с авторизацией дополнительно задайте `RAG_API_KEY` в окружении. Не сохраняйте ключ в репозитории. Пример локального совместимого API приведён в [документации Ollama](https://docs.ollama.com/api/openai-compatibility); формат Chat Completions описан в [документации OpenAI](https://developers.openai.com/api/reference/resources/chat). Установку и запуск самого сервиса генерации выполняют отдельно. В текущем окружении проекта генератор не настроен.

Дополнительные настройки:

| Переменная | Значение |
|---|---|
| `RAG_EMBEDDING_BACKEND` | `auto` по умолчанию: использовать backend имеющегося индекса; `hash` или `sentence-transformers` — перестроить индекс в указанном режиме |
| `RAG_EMBEDDING_MODEL` | Идентификатор локальной модели эмбеддингов для `sentence-transformers` |
| `RAG_INDEX_PATH` | Другой путь к SQLite-индексу |
| `RAG_MIN_SCORE` | Минимальное сходство фрагмента; по умолчанию `0.25` для `hash`, `0.35` для семантических векторов |
| `RAG_TIMEOUT_SECONDS` | Ожидание ответа генератора; по умолчанию 40 секунд |

Для семантического поиска установите `sentence-transformers` и перестройте индекс командой `venv/bin/python main.py vector-build --backend sentence-transformers`. Текущий индекс использует `hash`: это векторный, но преимущественно лексический поиск. Для вопросов без нужной карточки поиск в этом режиме дополнительно проверяется лексическим поиском, чтобы не отправлять модели случайные фрагменты.

## Обработка вопроса

1. Сервер читает Markdown-карточки. Если в вопросе указан ID, работает существующая обработка точных ID.
2. При наличии `RAG_BASE_URL` и `RAG_MODEL` индекс проверяется на актуальность и при необходимости обновляется. В длинных карточках выбираются наиболее близкие фрагменты; контекст ограничен шестью фрагментами, тремя фрагментами на карточку и тремя карточками.
3. Генератор получает вопрос и только выбранный контекст. Системная инструкция требует отвечать по материалу карточек, игнорировать инструкции внутри материала, добавлять ID источников в формате `[[ID]]` и воздерживаться при недостатке данных.
4. Ответ без ссылок или со ссылками на отсутствующие в контексте ID не показывается как RAG-ответ. В `sources` попадают только карточки, процитированные в ответе; браузер открывает их через `/cards/{id}`. Поле `is_rag_enabled` в таком ответе равно `true`.
5. Если генератор не настроен или недоступен, чат возвращается к прежнему лексическому поиску и показу карточки. Если модель сообщает о недостатке данных, чат отвечает, что подходящего материала нет.

Ответ по RAG отличается от полной карточки: он составлен моделью и может ошибаться, даже если ссылки корректны. Наличие ID подтверждает происхождение фрагмента, но не проверяет каждое утверждение в ответе. Перед эксплуатацией следует проверить качество на реальных вопросах и при необходимости настроить порог сходства, модель эмбеддингов и модель генерации.

## Проверка

```bash
venv/bin/python main.py vector-status
venv/bin/python -m pytest tests/ -q
```

Для ручной проверки задайте вопрос веб-чату и проверьте `POST /api/ask`: у сгенерированного ответа `is_rag_enabled: true`, в тексте стоят `[[ID]]`, а `sources` содержит ссылки на те же карточки. Без настроенной модели значение остаётся `false`.
