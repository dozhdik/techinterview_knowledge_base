# Проверка потокового RAG, 24.11.2026

## Методика

Linux Mint, Ollama 0.40.17, локальный API. Рабочий индекс и его копия имели одинаковый SHA-256 `257ae56b587d1276df5e85c86382dfc7b412a7d6563f1bb15f3792bfd00a991c`; индекс не перестраивался. Использовались реальные модель эмбеддингов, Ollama и HTTP FastAPI, без подмены ответов модели. При генерации `ollama ps` сообщил 100% GPU для обеих моделей.

Для сравнения LLM использованы один вопрос о хеш-таблице, одинаковый контекст 1582 байта (`CS-QUESTION-002:000` и `:001`), temperature 0.3, num_ctx 4096, num_predict 512 и keep_alive 15m. Для 8B явно задано `think=false`; для 4B Instruct параметр не задавался. Перед холодным запросом соответствующая модель выгружалась через API; повторный выполнялся сразу с той же моделью и промптом. Время первого токена — время вызова Ollama без поиска и загрузки эмбеддингов. Скорости рассчитаны по метрикам Ollama; время в секундах.

Очень высокая расчётная скорость повторной обработки входа отражает повторное использование промпта Ollama, а не независимую обработку всех входных токенов. 8B выдала меньше выходных токенов, поэтому сравнение общего времени не означает, что она быстрее генерирует. Оба ответа 4B в этом сравнении содержали искажённый ID `CS-QUESTION-0-02`: строгая проверка приложения должна их отклонить. Это измерения, а не гарантия качества.

## Поиск до и после

В отдельных процессах на той же копии индекса трижды выполнен запрос «Чем отличается поиск в ширину от поиска в глубину?». До изменений: 8,524 / 2,038 / 2,012 с; после: 7,606 / 0,492 / 0,206 с. Порядок ID совпал, первой была `CS-QUESTION-003`. Это единичные измерения, а не статистический бенчмарк. Первый потоковый запрос в отдельной проверке получил первый видимый текст через 16,24 с, второй — через 4,31 с; полное время зависело от длины ответа.

## Функциональные наблюдения

Реальный поток 4B для хеш-таблицы и BFS/DFS вернул проверенные источники `CS-QUESTION-002` и `CS-QUESTION-003`; в текстовых чанках не обнаружено `[[`. В ответе о хеш-таблице модель привела порог 0,7–0,8, которого не было в переданном фрагменте. Для behavioral interview получен источник `PROC-STAGE-005`; детали ответа требуют фактологической проверки. Первый запрос о балансировщике был отклонён из-за неверной ссылки. После этого в запрос модели добавлен явный список разрешённых ID. По горизонтальному/вертикальному масштабированию поиск не вернул достаточно точного совпадения, а по квантовой запутанности вернул отказ. Ошибка ссылки или частичное утверждение не доказывает отсутствие аналогичных ошибок на других вопросах.

Модульный тест проверяет закрытие upstream-соединения при отмене; он не является измерением освобождения GPU самим Ollama. На 360 и 1280 px Chromium проверены запуск интерфейса и запрос карточки по ID. Проверка ссылок ограничивается принадлежностью контексту, а системная инструкция не гарантирует фактологическую корректность и устойчивость к инструкциям в недоверенных документах.

## Повтор после уточнения списка источников

Повторный запрос о балансировщике вернул корректный `ARCH-COMPONENT-001` за 100,40 с (первый видимый текст через 14,10 с при холодной загрузке эмбеддингов). Повторный запрос хеш-таблицы вернул `CS-QUESTION-002` за 117,04 с (первый видимый текст через 3,14 с), но снова включил отсутствующий в фрагменте численный порог 0,7–0,8. После этого добавлена узкая проверка десятичных значений против переданного контекста: подобный ответ должен отклоняться. Она не проверяет остальные факты и может отклонить корректный расчёт, отсутствующий в контексте буквально.

В реальном Chromium на 360 px поток начал появляться, кнопка остановки стала доступна, а сообщение об остановке появилось через 0,092 с; JavaScript-ошибок не было. При проверке обнаружено и затем исправлено горизонтальное переполнение формы. Закрытие upstream-соединения отдельно проверено автоматическим тестом; фактическое прекращение вычислений на GPU Ollama независимо не измерялось.

Отдельный реальный HTTP-запрос к потоковому API с недоступным адресом Ollama вернул карточку в резервном режиме (`is_rag_enabled=false`). Проверка прямого ID и отдельной ссылки на источник повторно прошла в Chromium на 360 и 1280 px без переполнения и ошибок JavaScript.

После добавления числовой проверки выполнен ещё один реальный потоковый запрос по хеш-таблице: первый текст появился через 10,87 с, но через 143,71 с итог был отклонён, поскольку модель снова добавила десятичное значение вне контекста. Предварительный текст не был принят как проверенный ответ. Это показывает, что защита полезна, но не решает проблему качества модели: пользователь может получить отказ даже при наличии релевантной карточки.
