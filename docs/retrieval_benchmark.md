# Проверка информационного поиска TechInterview

## Аудит корпуса

Проверены все Markdown-карточки в наполненных областях. В CS 77 карточек, в архитектуре 76, в подготовке к собеседованиям 75. Всего 228 карточек и 15 категорий. В `global` карточек нет. Медианная длина Markdown — 1 245,5 символа, диапазон — от 956 до 5 681. У 163 карточек тело короче 2 000 символов. Проверка по нормализованному тексту не нашла полных дубликатов. Она не оценивает смысловые повторы, например пересечение карточки алгоритма с задачей о его применении.

У всех карточек есть источники, роли и теги. Найдены 293 разных тега, 492 ссылки `related` и 152 ссылки `prerequisites`. Все указанные в этих полях ID существуют. Раздел «Главное» встречается 165 раз, «Пример» — 107, «Определение» — 57. Встречаются вложенные заголовки, таблицы, списки, блоки кода и смешанная русско-английская терминология. Эти свойства используются как поля поиска и границы фрагментов. Содержимое карточек при эксперименте одинаково.

Исходный индекс содержал 621 фрагмент размерности 384. Токенизатор установленной модели насчитал больше 128 токенов у 435 из них, максимум 404. Старое ранжирование сначала отбрасывало фрагменты по пересечению слов и затем считало косинусное сходство. Экстрактор выбирал разделы одной карточки. Новый индекс хранит 1 861 оригинальный блок и 2 012 векторных окон. Максимум на блок — три окна. Эмбеддинги используют до 128 токенов на окно. Пользователю возвращаются оригинальные блоки либо компактный родительский раздел.

## Методика

В [машиночитаемом наборе](../evaluation/search_cases.json) 185 вопросов по трём областям. 125 относятся к development и 60 к test. В test 53 положительных и 7 отрицательных вопросов. Метки составлены по заголовкам и текстам карточек до просмотра поисковой выдачи. Карточки с положительными метками разделены между выборками, переформулировки одной карточки остаются вместе. Три случая с разметкой по нескольким карточкам относятся к development. Независимая численная оценка составных вопросов этим набором не обеспечена.

На development сравнивались исходный поиск, два независимых канала, RRF, покрытие, пороги отказа, одношаговые связи и Cross-Encoder. Снижение веса семантического списка в RRF с 0,70 до 0,45 улучшило Precision@1 и покрытие проверяемых фрагментов. BM25 использует веса 2,6 для названия, 1,4 для заголовка, 1,5 для тегов и 1,0 для текста. Название и теги описывают тему всей карточки, заголовок — локальный смысл. IDF считается по карточкам, чтобы длинные документы с повторяющимися заголовками не уменьшали значимость терминов. Каждый канал даёт до 30 уникальных карточек. RRF объединяет позиции с константой 12. Проверка достаточности учитывает покрытие и сходство, а для семантических совпадений без словесной опоры также отрыв от следующего кандидата.

Метрики ранжирования рассчитаны по уникальным карточкам. Precision@k делит число совпадений на k. Неразмеченные альтернативы считаются нерелевантными при подсчёте. Разметка покрывает один основной источник на большинство вопросов. Покрытие фактов и разделов — автоматические прокси по буквальным фразам и заголовкам с проверкой ID источника. Такое измерение пропускает часть корректных формулировок и может засчитать неполный ответ. Полнота и достоверность всех утверждений не проверены независимо.

Среда замера — Linux, Python 3.12.3, Sentence Transformers 6.3.0 и 18 логических CPU. MiniLM загружен из локального снимка `e8f8c211226b894fcb81acc59f3b34ba3efd5f42`. Отпечаток корпуса `593c77a07f9e15a105d9226dd31263027a0e38382ec052f578b3aa2b896895d6`. Cross-Encoder — [mMARCO MiniLMv2](https://huggingface.co/cross-encoder/mmarco-mMiniLMv2-L12-H384-v1), Apache-2.0, 471 МБ весов safetensors, снимок `1427fd652930e4ba29e8149678df786c240d8825`. На CPU модель получала до 12 пар вопрос–фрагмент одним вызовом. Для основных запусков использовались OMP_NUM_THREADS=2 и OPENBLAS_NUM_THREADS=1, для Cross-Encoder OMP_NUM_THREADS=4. Другие модели эмбеддингов и span QA не запускались.

### Ручная сверка извлечения

Для ручной сверки взят каждый пятый вопрос отложенного прогона, начиная с первого. Ответы сопоставлены с текстом карточек. Выбор дал 12 запросов. Три ответа закрывают вопрос полностью, два частично, один не отвечает по существу. Из шести отказов два корректны, для четырёх в корпусе были материалы. У шести выданных ответов фактические фрагменты присутствуют в указанных источниках. При сверке оценивались соответствие вопросу и точность переноса текста из источника. Фактические утверждения самих карточек по внешним источникам не перепроверялись.

| Ручная оценка | Вопросы |
| --- | --- |
| Полный ответ | Порядок поиска в BST, худший случай для hash map, подготовка к coding-интервью |
| Частичный ответ | Переход к микросервисам, аргументация инженерного выбора |
| Нерелевантный ответ | Фиксация и откат в БД |
| Необоснованный отказ | Очередь фоновых работ, внешний reverse proxy, компенсация шагов распределённой операции, рекурсивный DFS на длинной цепочке |
| Корректный отказ | Квантовая запутанность, настройка SAP HANA |

В ответе о переходе к микросервисам таблица и примеры дают ориентиры, но подбор также включает детали отладки монолита и пропускает исходное объяснение условия перехода. У ответа про BST основной алгоритм изложен полностью, а детали вставки и удаления добавляют лишний контекст. В ответе о техническом выборе альтернативная карточка подходит по смыслу, хотя benchmark её не засчитывает. По совпадению с этой карточкой виден общий подход, а раскрытие критериев осталось в другом разделе.

Для гибрида медианы этапов в отложенном прогоне составили эмбеддинг 47.1 мс, retrieval 3.2 мс, переоценка 2.6 мс, извлечение 0.1 мс.

В исходном прогоне с прогретой моделью снятие метаданных индекса заняло 0,51 с. В холодном прогоне гибрида чтение метаданных и подготовка поисковых структур заняли 0,97 с, загрузка модели вошла в 9,57 с первого запроса. В отдельной HTTP-проверке холодный ответ о BFS занял 10,874 с с загрузкой MiniLM. Прогретый составной вопрос занял 0,164 с, отказ — 0,084 с, прямой ID — 0,025 с. Открытие ссылок на источники проверено по HTTP.

Выбор по development — гибрид с лёгкой переоценкой по покрытию терминов. Одношаговый обход связанных карточек почти не изменил ранжирование и не улучшил извлечение. Cross-Encoder увеличил задержку и снизил покрытие фактов на development. Он доступен только через настройку локального пути. Чистый RRF на test немного выиграл в ранжировании у выбранного варианта, при одинаковом покрытии фактов. Это расхождение с development оставлено в отчёте.

Детализация по категориям и конфигурации доступны в [JSON с результатами](../evaluation/search_results.json). CLI `search-benchmark` сохраняет выдачу, извлечённый текст и время для каждого вопроса. Проверки проекта — 270 тестов. Индекс фрагментов прошёл `PRAGMA integrity_check`.
